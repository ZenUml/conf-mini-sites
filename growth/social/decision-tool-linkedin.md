# LinkedIn Post Draft — Decision Tool Scenario

Every vendor-selection doc I've ever reviewed had the same table: options down the side, criteria across the top, a bolded "winner" at the bottom. And every time, my honest reaction was — I don't trust this. Not because the analysis was wrong, but because I couldn't see how it was produced. Someone else picked the weights.

So while building Mini Sites, I stopped shipping the table and started shipping the tool that produces it. Instead of a static grid, I embed a live decision tool on the page: readers drag sliders to set how much Cost, Impact, Risk, and Effort matter to them, and the ranking recomputes in front of them. Same underlying scores, but now the reader is testing the recommendation with their own priorities instead of accepting yours.

It's a small shift, but it changes the conversation from "why did you rank B first" to "here's what happens when I weight risk higher" — which is a much better conversation to be having before a decision gets made.

This is the pattern I keep coming back to with Mini Sites: take the thing stuck as static prose or a table nobody trusts, and make it something people can actually operate, inline, right where the decision is being written up.

If you write vendor comparisons, architecture proposals, or any doc with a "which option wins" table in Confluence — give Mini Sites a try on the Atlassian Marketplace.
